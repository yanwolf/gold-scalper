# 黃金極短線分析工具

架構參考自 crypto-screener：Python/FastAPI 後端 + 前端頁面同源提供。
資料層 + 分析層(分價量表/纏論) + 簡易視覺化 dashboard 都已經可以動，
下一步是訊號邏輯設計和接軌 MT5 自動下單。

## 資料源

- **Binance XAUUSDT 永續合約（主力資料源）**：24/7 交易（含週末），tick級即時WebSocket，
  不需要API Key。分析模組(K線、分價量表、纏論)固定用這條線的逐筆成交(aggTrade)真實成交量。
  是衍生品合成價格，不是實體黃金或COMEX期貨本身，只作為目前的開發用資料源，不應該當作最終下單依據。
- **OANDA XAU_USD（暫緩）**：申請流程需要桌機才能完成「Manage API Access」設定，手機無法申請，先擱置。
  未來接軌CFD執行端時，這裡的角色可能會被實際下單的經紀商取代（見下方MT5備忘）。
- ~~GoldAPI.io~~：已移除。免費方案只有每月100次請求額度，撐不住持續輪詢，架構因此簡化為Binance單一主力資料源。

## 部署到 Zeabur

1. 把這個資料夾推到 GitHub repo（`.env` 不會被推上去，這是故意的）
2. Zeabur 建立新服務，選這個 repo，會自動偵測 `Dockerfile` 並用容器方式建置
3. 環境變數（可先什麼都不填，服務一樣能正常啟動）：
   - `BINANCE_GOLD_SYMBOL`（預設 xauusdt，不用改也可以）
   - `DATABASE_URL`（見下方「資料持久化」章節）
   - `OANDA_API_TOKEN` / `OANDA_ACCOUNT_ID`（之後有機會用電腦申請完再補）
4. 不用手動設定 `PORT`，Zeabur 會自動注入
5. 部署完打 `/health`，確認 `binance_stream.connected` 是 `true`
   （`oanda_stream.connected` 目前預期是 `false`，屬正常狀態）

## 資料持久化：PostgreSQL

Zeabur重新部署或容器重啟，記憶體裡的tick/trade歷史本來會被清空，分析模組(尤其纏論的
5分鐘K線)每次都要重新累積資料才能用。`app/db.py` 解決了這個問題：把Binance逐筆成交批次
寫進PostgreSQL，服務啟動時自動從資料庫回填歷史資料到記憶體。

**設定步驟：**
1. Zeabur專案裡新增一個服務：Marketplace搜尋 **PostgreSQL**，一鍵部署
2. 回到 gold-scalper 服務的環境變數頁，新增：
   ```
   DATABASE_URL=${POSTGRES_CONNECTION_STRING}
   ```
   （Zeabur的變數引用語法，會自動抓PostgreSQL服務的連線字串，不用手動複製帳密）
3. 重新部署後打 `/health`，確認 `database_persistence_enabled` 是 `true`

**運作方式：**
- 每20秒把新累積的逐筆成交批次寫進資料庫一次
- 服務啟動時自動從資料庫回填最近的歷史成交進記憶體(上限 `MAX_TRADE_HISTORY`，目前20000筆)
- **沒設定 `DATABASE_URL` 也完全沒問題**：自動退回純記憶體模式，不會讓服務起不來
- 寫入/讀取失敗只記錄log，不會讓即時資料流中斷

## 分析模組

`app/analysis.py`，資料源固定用 Binance 的逐筆成交(aggTrade)，因為只有這條線有真實成交量。

三個 endpoint：
- `GET /analysis/candles?interval_seconds=300` — K線聚合，預設5分鐘，改參數可切其他週期(如60=1分鐘)
- `GET /analysis/volume-profile?bucket_size=1.0` — 分價量表，含POC(成交量最大價位)和Value Area(70%成交量區間)
- `GET /analysis/chan?interval_seconds=300` — 纏論分析：分型 -> 筆 -> 中樞 -> 背馳判斷

**纏論邏輯的實作範圍(第一版)：**
- 分型/筆/中樞用標準教學版簡化規則實作，已用合成資料測試過能正常產出結果
- 背馳判斷用MACD柱狀圖面積比較「同方向筆」的動能是否縮小，屬於簡化版，還沒處理盤整背馳、趨勢背馳的細分類
- 目前只抓「三筆重疊」的基本中樞，還沒做中樞延伸/擴張的判斷邏輯

## 未來接 MT5 自動交易的架構備忘

MT5 官方 Python 套件只能在 Windows、且要跟正在執行的 MT5 終端機同一台機器運作，Zeabur(雲端Linux容器)
沒辦法直接跑MT5。之後的分工建議：
1. 這個 Zeabur 服務持續負責訊號生成，新增一個 `/signal/latest` endpoint
2. 另外一台 Windows VPS 跑 MT5 終端機 + 一個 MQL5 寫的 EA，EA 用 `WebRequest()` 定期輪詢
   `/signal/latest`，收到訊號後用 MT5 原生下單函式執行
3. 兩邊分離，訊號邏輯迭代不用碰 Windows/MT5 那一側
4. 執行端經紀商(例如 Exness、IC Markets 等提供 MT5 的CFD商)確定後，該經紀商的報價會自然成為
   「主要訊號源」，取代目前暫緩的OANDA角色，確保訊號跟執行價格基準一致

## 修正記錄

**Binance WebSocket 路由分流 (2026)**：Binance 把 WebSocket 資料流拆成 `/public`、`/market`、
`/private` 三個路由，`bookTicker`(報價)屬於`/public`，`aggTrade`(逐筆成交)屬於`/market`。
沒有指定路由的舊式連線只會收到`/public`的資料，`/market`底下的頻道會被靜默丟棄(不報錯，就是
收不到)。`binance_client.py` 已修正為兩條獨立連線分別接兩個路由，`/health` 的 `binance_stream`
有 `public_connected` / `market_connected` 兩個欄位可以分別檢查。

## 訊號引擎：綜合纏論 + 分價量表

新增 `app/signal.py`，把纏論和分價量表的判斷綜合成一個分階段的多空訊號，
不是機器學習模型，是規則式(rule-based)判斷，每條規則對應標準的纏論/Volume Profile概念，
方便之後逐條檢視、調整權重。

**判斷規則：**
- 纏論那一側：背馳反轉(優先權較高，因為是提早示警) > 中樞突破(站上ZG看多/跌破ZD看空) > 中樞內整理(中性)
- 分價量表那一側：站上/跌破Value Area(強訊號) > 相對POC偏移(弱訊號)
- 綜合：兩邊方向一致+至少一邊強 -> **訊號**；兩邊方向一致但都弱，或只有單邊有方向 -> **關注**；方向衝突 -> **中性**

**Endpoint：** `GET /signal/latest?interval_seconds=300&bucket_size=1.0`
回傳 `stage`(訊號/關注/中性)、`direction`(bullish/bearish/null)，以及纏論、分價量表兩側各自的判斷理由。
這是未來要給MT5 EA輪詢的endpoint，格式先在這裡驗證穩定，之後EA可以直接用`WebRequest()`定期打這支API。

Dashboard最上方新增了訊號面板：不同階段/方向會有不同配色(訊號=強烈發光框、關注=金色、中性=素色)，
下方列出纏論和分價量表各自的判斷理由，方便直接看懂「為什麼」給這個訊號，不是黑盒子。

## K線圖（Dashboard）

## 修正記錄：訊號面板與分價量表POC數字不同步

`fetchSignal()` 原本把 `/signal/latest` 的 `trade_limit` 參數寫死成20000，
但下方分價量表面板用的是使用者自己選的「近N筆」下拉選單(1000/3000/6000)，
兩邊取樣範圍不同，算出來的POC/VAH/VAL自然對不上。已修正成兩處共用同一個
`els.tradeLimit` 的值，確保訊號框跟分價量表、K線圖上疊加的水平線永遠是同一組數字。

## 修正記錄：架構性修正 — 統一成單一資料快照

前一版的修正(讓trade_limit參數對齊)只解決了表面症狀，實際上還會不同步：
因為訊號框跟分價量表面板是**分開打兩支API**，Binance報價持續在跳動，
兩次獨立呼叫`get_recent_trades()`的時間點不同，「最近N筆成交」這個窗口
會跟著往前推移，算出來的POC自然對不上——尤其在價格快速變動時特別明顯。

**根本修正**：`/signal/latest` 現在在後端只呼叫一次`get_recent_trades()`，
`chan_detail`(完整纏論分析)和`profile_detail`(完整分價量表)都是從同一份
trades快照算出來的，一併包在回應裡回傳。前端 `fetchAndRender()` 也跟著
簡化成只打這一支API，分價量表、纏論分析、訊號框、K線圖上的水平線全部
從同一份回應取資料渲染，不再各自獨立打API，架構上保證永遠同步。

`/analysis/chan`、`/analysis/volume-profile` 這兩支獨立endpoint還留著
(給之後debug或其他用途單獨查看用)，但dashboard本身已經不再使用它們。

## 修正記錄：纏論資料不足問題

上一版把 chan_data 和 profile_data 綁在同一個 `trade_limit` 參數上(解決同步問題)，
卻意外造成新問題：分價量表刻意設計成只看「近3000筆」這種小範圍，但纏論需要更長的
歷史資料才能拼出足夠K棒(尤其1分鐘K線)，導致纏論常常「尚未形成中樞」、「筆數0」。

**修正**：纏論和分價量表仍然共用同一次 `get_recent_trades()` 呼叫(保持同步)，
但纏論固定用較大的回看範圍 `CHAN_LOOKBACK_TRADES`(20000筆)，分價量表則從這份
資料裡再切出使用者指定的 `trade_limit`(較小範圍，符合「看近期熱區」的設計本意)。
兩者是同一份快照的不同切片，既同步、又各自有適合的資料量。

## Telegram 訊號通知（純通知/觀察階段）

`app/notifier.py` 背景每30秒(可用`NOTIFY_POLL_SECONDS`調整)直接在後端計算一次訊號
(重用analysis/signal的邏輯，不透過HTTP)，當階段變成「訊號」時透過Telegram Bot
發送通知到手機。**目前只通知，不會自動下單**，這是接軌未來Pepperstone MT5自動執行前
的觀察階段，先驗證訊號品質。

**設定步驟(手機可完成)：**
1. Telegram搜尋 `@BotFather`，傳送 `/newbot`，照指示取得一組 **Bot Token**
2. 跟你剛建立的bot隨便傳一句話(觸發對話)
3. 瀏覽器打開 `https://api.telegram.org/bot<你的TOKEN>/getUpdates`，
   從回傳JSON裡的 `message.chat.id` 找到你的 **Chat ID**
4. 在Zeabur環境變數新增：
   ```
   TELEGRAM_BOT_TOKEN=你的bot token
   TELEGRAM_CHAT_ID=你的chat id
   ```
5. 重新部署後打 `/health`，確認 `telegram_notifier_enabled` 是 `true`

**防重複通知邏輯：** 只有訊號「新升級成訊號階段」或「訊號方向反轉」時才會發送，
同一個訊號不會每30秒重複騷擾。已用模擬情境測試過這個邏輯。

**未來要接真正下單時的路徑：** 這個模組目前只做`_send_telegram_message()`，
之後正式接Pepperstone MT5執行時，可以在同樣的判斷點(訊號升級/反轉時)，
改成呼叫真正的下單邏輯(或是維持通知，另外讓MT5 EA自己輪詢`/signal/latest`
做下單判斷，兩者可以並存)。

## Dashboard 新增：Telegram 通知設定面板

不用再手動打Telegram API網址查JSON，dashboard最下方新增了「Telegram 通知設定」面板：

- **連線狀態燈號**：綠色=已連接且運作中、金色=已連接但暫停中、紅色=尚未設定Token/Chat ID
- **傳送測試通知**：立刻打一則測試訊息到你的Telegram，確認設定是否正確
- **暫停/恢復通知**：不用重新部署就能暫停(這是記憶體狀態，服務重啟會重置回「未暫停」)
- **尋找我的 Chat ID**：呼叫Telegram的`getUpdates`，列出最近跟你的bot說過話的對話，
  按一下就能複製對應的Chat ID，不用自己組網址、找JSON欄位

**新增的API endpoint**(`app/notifier.py` + `main.py`)：
- `GET /notify/status` — 連線/暫停狀態、上次通知時間
- `POST /notify/test` — 傳送測試通知
- `POST /notify/toggle?muted=true|false` — 暫停/恢復
- `GET /notify/detect-chat-id` — 列出最近的對話，找Chat ID用

流程還是一樣：Token/Chat ID本身要透過Zeabur環境變數設定(`TELEGRAM_BOT_TOKEN`、
`TELEGRAM_CHAT_ID`)，dashboard面板負責「找到正確的Chat ID」和「驗證設定有沒有生效」，
不會把Bot Token直接暴露在前端頁面上(安全考量，Token只存在後端環境變數)。

## 修正記錄：預設週期改成1分鐘K線

纏論(分型/筆/中樞)在5分鐘K線下需要收集比較久的資料才夠判斷，1分鐘K線能更快
驗證多空進出場的時機點。已把預設週期從5分鐘改成1分鐘：
- `app/notifier.py` 的 `DEFAULT_INTERVAL_SECONDS`（Telegram通知判斷用）
- `/signal/latest` 的 `interval_seconds` 預設值
- dashboard的K線週期下拉選單，預設改選「1分鐘K線」

之後想切回5分鐘或15分鐘，dashboard上直接切換下拉選單即可即時查看；
Telegram背景通知的判斷週期則需要改`DEFAULT_INTERVAL_SECONDS`後重新部署才會生效。

## 模擬單績效追蹤（正式接自動下單前的驗證階段）

新增 `app/paper_trading.py`，在訊號階段升級成「訊號」時虛擬開一筆倉位(不是真的

## 修正記錄：固定停利改成移動停損

固定停利在順勢單邊行情下會提早出場、吃不到後面延伸的漲跌幅，出場後只能乾等。
已把出場邏輯從「固定停損停利」改成「移動停損(Trailing Stop)」：

**運作方式：**
1. 進場時用固定的保守停損(`PAPER_SL_POINTS`，預設3.0)保護，避免立刻被小波動洗出去
2. 價格往有利方向前進到一定距離(`PAPER_TRAIL_TRIGGER_POINTS`，預設3.0)後，「啟動」移動停損
3. 啟動後，停損價位跟著峰值價持續往有利方向移動，永遠只距離峰值
   `PAPER_TRAIL_DISTANCE_POINTS`(預設3.0)，讓利潤隨趨勢延伸，直到回檔碰到停損才出場
4. 停損只會往有利方向移動，不會因為價格反彈/回檔而放寬(單向棘輪機制)
5. 訊號反轉時依然會出場(這條規則保留，跟移動停損並存)

已用模擬強勢單邊行情測試過：同樣的價格路徑，固定TP=6只能拿到6.0 points，
改用移動停損後拿到11.5 points，也驗證過停損不會因價格反彈而錯誤放寬。

資料庫schema新增 `peak_price`、`trailing_active` 欄位取代原本的 `tp_price`，
舊資料庫會自動升級(用`ADD COLUMN IF NOT EXISTS`，不影響既有資料)。

Dashboard的開倉狀態卡片也更新了，會顯示「移動停損已啟動」/「尚未啟動」的狀態徽章，
以及目前的停損價位和峰值價格。

這次新增三塊互相搭配的功能，目的是不用乾等即時模擬單累積樣本，就能先評估
這套訊號邏輯值不值得正式接軌Pepperstone MT5執行。

### 架構重構：共用交易邏輯

新增 `app/trading_core.py`（純函式：開倉/移動停損更新/出場判斷/平倉計算，
不碰資料庫、不碰背景執行緒）和 `app/trading_stats.py`（績效統計 + 達標門檻評估）。
`paper_trading.py`(即時模擬單) 和 `backtest.py`(歷史回測) 都呼叫同一套這些函式，

### 歷史回測

`app/backtest.py`：抓Binance期貨過去N天(上限7天)的1分鐘K線，因為K線本身沒有
逐筆明細，用開高低收各帶1/4成交量還原成合成成交(近似值，分價量表精細度比
即時模式粗糙一些，但足夠抓策略大方向表現)。用walk-forward方式逐根K線重播，
每一步只用「當下時間點為止」的資料計算訊號，避免用到未來資料(look-ahead bias)。

**Endpoint：** `GET /backtest/run?days=2` (可調 interval_seconds/bucket_size/
trade_limit/sl_points/trail_trigger_points/trail_distance_points，預設值
跟即時模擬單一致)

### 績效統計加最大回撤

`trading_stats.compute_stats()` 現在會算最大回撤(Max Drawdown)：把交易依時間
排序、算累積損益曲線，抓「從歷史高點回落最多」的那一段(points)。這是評估
「連續虧損最慘會虧多少」的關鍵風險指標，即時模擬單和回測都會顯示。

### 達標門檻

`trading_stats.assess_readiness()` 對照以下門檻(都可用環境變數調整)，
四項全部通過才會判定為「已達標」：
- 樣本數 ≥ `READINESS_MIN_TRADES`(預設30筆)
- 勝率 ≥ `READINESS_MIN_WIN_RATE`(預設40%)
- 獲利因子 ≥ `READINESS_MIN_PROFIT_FACTOR`(預設1.3)
- 最大回撤 ≤ `READINESS_MAX_DRAWDOWN_POINTS`(預設30 points)

這不是獲利保證，只是避免樣本數太少或績效不夠穩定就貿然接真錢。
`/paper-trading/summary` 和 `/backtest/run` 的回應都會包含 `readiness` 欄位。

## 背景執行緒健康監控與告警

新增 `app/health_monitor.py`，定期檢查關鍵背景元件是否正常運作，異常時透過
Telegram主動告警（跟訊號通知共用同一個Bot，但防重複邏輯完全獨立），不用再
自己手動查 `/health` 才會發現問題。問題恢復時也會發一則「已恢復」通知。

**監控項目：**
1. **Binance連線**：`public`/`market`兩條路由斷線超過`HEALTH_DISCONNECT_THRESHOLD_SECONDS`
   (預設120秒) -> 告警
2. **成交資料是否卡住**：即使顯示已連線，也可能資料實際上沒在更新(連線假死)，
   用`trade_count`是否持續增加做二次確認，卡住超過`HEALTH_TRADE_STALL_THRESHOLD_SECONDS`
   (預設300秒) -> 告警
3. **模擬單追蹤引擎心跳**：太久沒執行過檢查(超過`HEALTH_PAPER_STALL_THRESHOLD_SECONDS`，
   預設180秒) -> 可能背景執行緒掛了 -> 告警
4. **Telegram通知執行緒**：設定了Token/ChatID卻執行緒沒有存活 -> 告警(這則告警本身
   走獨立的Telegram發送路徑，不受影響，還是送得出去)
5. **資料庫寫入健康度**：有接資料庫的話，最近一次寫入失敗 -> 告警

**設計重點：**
- 每種檢查都有獨立的「目前是否告警中」狀態，只在問題「剛發生」或「剛恢復」時
  發送通知，不會每個檢查週期都重複騷擾
- 已用模擬情境測試過所有告警的狀態轉換邏輯(發生時通知一次、持續中不重複、
  恢復時通知一次)
- 沒有設定Telegram也完全沒問題，狀態一樣會持續在背景檢查、記錄，只是不會主動推播，
  可以透過 `GET /health/monitor` 隨時查看目前狀態

**Endpoint：**
- `GET /health/monitor` — 最後檢查時間、目前有哪些告警在生效中、每項檢查的完整狀態
- `GET /health` 也新增了 `active_health_alerts` 欄位，方便一次看到全貌

**Dashboard：** 最上方新增健康告警橫幅，有任何異常時會顯示紅色警示列表，正常時不顯示任何東西(不佔版面)。

## 修正記錄：健康監控誤報「Binance成交資料已停滯」

原本用`trade_count`(逐筆成交筆數)是否持續增加來判斷資料有沒有卡住，但這個數字
背後是一個容量上限20000筆的緩衝區(`deque(maxlen=20000)`)，一旦成交量累積超過
上限，筆數就會卡在20000不再變化(因為每加一筆新的就會擠掉最舊一筆，總數不變)，
即使資料其實仍在正常更新——這是計數方式的設計缺陷，不是真的資料源出問題。

**修正**：改用「最新一筆成交的實際時間」離現在多久來判斷，而不是看筆數變化。
`binance_client.py`的`status`新增`latest_trade_time`欄位(最新一筆成交的時間戳)，
`health_monitor.py`改成比對這個時間戳的新舊程度。已用模擬情境測試過：
trade_count卡在上限但資料仍在更新時不會再誤報，只有latest_trade_time真的
過期才會正確告警。

## 修正記錄：回測7天會讓整個服務凍結

### 問題1：O(n²)的重播邏輯

原本每一步重播都用 `[t for t in trades if t["time"] <= step_time]` 重新掃過
整份合成成交清單，7天資料約4萬筆、上萬個時間步驟，等於要做上億次比對，
純Python執行極慢(實測7天需要122秒)。

**修正**：改用`bisect`在已排序的時間清單上做二分搜尋定位邊界，並且每一步只保留
最近`CHAN_LOOKBACK_TRADES`筆(這也是纏論分析內部實際會用到的上限)，避免切片
大小隨著回測進度不斷成長。

### 問題2：同步運算卡住整個FastAPI事件循環

`/backtest/run`雖然宣告成`async def`，但直接呼叫同步、吃CPU的`run_backtest()`，
這會讓運算期間整個服務(health check、dashboard、Binance背景資料接收全部)
被凍結，這才是「按下回測7天、整個網頁掛掉」的真正原因，不只是回測本身跑很久。

**修正**：改用`asyncio.to_thread()`把運算丟到背景執行緒，事件循環在運算期間
保持暢通，其他請求不會被卡住。

### 問題3：即使修正後，長天數回測還是太慢

修正O(n²)後，7天仍要122秒，遠超過一般HTTP請求能負擔的時間(Zeabur反向代理/
瀏覽器通常30-60秒就會逾時)。

**修正**：加入動態取樣間隔(stride)——重播步數的目標控制在`TARGET_STEP_COUNT`
(1200步)附近，天數短時每根K線都檢查(stride=1，保持最高精確度)，天數長時
自動跳著檢查(例如7天會用stride=8，只檢查每8根K線一次)，犧牲一些時間精確度
換取能在合理時間內跑完。回應裡新增`replay_step_count`和`replay_stride`欄位，
dashboard會顯示目前這次回測用的取樣間隔。

修正後實測(合成資料)：1天3.8秒、2天7.1秒、3天11.3秒、5天13.3秒、7天15.3秒，
全部都在安全範圍內。

## 優化：移動停損太緊 + 訊號反轉太頻繁被雜訊洗出場

實際運作後發現黃金日內雜訊波動常常超過3點，原本的移動停損參數(3/3/3)常常
在趨勢還沒真正走出來前就被正常雜訊觸發，加上訊號反轉出場沒有任何緩衝，
瞬間閃爍一次就會把倉位洗出場，兩者疊加侵蝕了獲利。

### 1. 拉寬停損/移動停損預設值

`PAPER_SL_POINTS`(初始停損): 3.0 -> **5.0**
`PAPER_TRAIL_TRIGGER_POINTS`(觸發移動停損所需獲利): 3.0 -> **6.0**
`PAPER_TRAIL_DISTANCE_POINTS`(移動停損跟峰值的距離): 3.0 -> **5.0**

這是第一階段的快速調整(拉寬固定點數)，下一步規劃是改成ATR動態版本，
跟著當下實際波動度自動調整距離，而不是猜一個固定數字。

### 2. 訊號反轉加上「連續確認」機制

`app/trading_core.py`的`check_exit()`新增`reversal_confirm_count`參數(預設2)：
反向訊號需要**連續兩次檢查都看到同一個方向**才算數才會真的出場，訊號瞬間
閃爍一次、下一次檢查又變回來的情況不會誤觸發出場。用position字典裡的
`pending_reversal_direction`/`pending_reversal_count`追蹤跨檢查週期的狀態：
- 連續看到同方向反向訊號 -> 計數累加，達標才出場
- 反向訊號的方向自己又變了、或訊號消失/降級 -> 計數歸零，重新開始算

注意：觸及停損(初始或移動後)**不受這個確認機制影響**，價格觸發就立即出場，
這條規則是價格層面的風控保護，不應該因為等訊號確認而延遲。

這個確認狀態目前只存在記憶體/資料庫的position記錄裡，服務重啟時不會回填
(重啟後從0開始重新計算確認次數)，是可接受的小限制，不影響停損本身的保護。

已用模擬情境測試過三種狀況：反向訊號閃爍一次不出場、連續兩次才出場、
停損不受確認機制影響立即出場，全部符合預期。

`/backtest/run` 新增 `reversal_confirm_count` 參數，預設值也跟即時模擬單一致(2)。

## 精進：中樞延伸判斷 + 趨勢/盤整背馳分類

**中樞延伸**：原本抓到3筆重疊就定義中樞、之後不再更新邊界，如果價格只是在
同一個區間內延伸震盪，會被誤判成「已經突破」(因為比對的是過時邊界)。
`_find_zhongshu()` 現在會持續檢查後續的筆是否還跟中樞範圍重疊，重疊就納入
延伸(邊界ZG/ZD不變，但涵蓋時間拉長、bi_indices增加)，直到真正出現完全不
重疊的筆才視為突破、中樞結束。回傳結果新增 `is_extended` 和 `bi_count` 欄位。

**趨勢背馳 vs 盤整背馳**：纏論裡這兩者可信度不同——趨勢背馳需要至少兩個
「不重疊」的中樞構成真正的趨勢結構，比較連接兩個中樞之間的走勢跟離開最新
中樞的走勢，代表整個趨勢動能衰竭；盤整背馳找不到這種結構時，退回比較最近
兩筆同方向走勢，範圍比較局部、可信度較低。`_find_trend_zhongshu_pair()`
負責判斷是否存在真正的趨勢結構，`_detect_beichi()` 依此決定用哪種比較方式，
回傳新增 `beichi_type` 欄位。

**這個分類現在會實際影響訊號強度**：`signal.py` 的 `_evaluate_chan_bias()`
依 `beichi_type` 給不同權重——趨勢背馳維持`strong`(單靠這個訊號源就能觸發
「訊號」)，盤整背馳降級成`weak`(需要分價量表那邊也給出強訊號才會一起升級
成「訊號」，否則停在「關注」)。已用端到端測試驗證：相同的背馳條件下，趨勢
背馳能觸發「訊號」，盤整背馳只會停在「關注」，符合預期的可信度分級效果。

Dashboard不用改，纏論面板本來就會顯示`beichi.detail`文字，新的
【趨勢背馳】/【盤整背馳】標籤會自動出現在裡面。

**下一步：** 已用合成資料驗證邏輯本身正確運作，實際對勝率/獲利因子有多少
提升，建議用回測比較改動前後的表現(可以用git紀錄回退測試，或保留一份舊版
邏輯的分支對照)。

## 新增：最大回撤發生區間

最大回撤(Max Drawdown)是「累積損益曲線從歷史高點到之後最低點」的落差，
**不等於總虧損**，這是兩個完全不同的概念。如果策略曾經帳面大賺一段、
後來又把獲利吐回去(甚至小幅由正轉負)，最大回撤可以遠大於最終的總損益數字
——例如帳面一度衝到+130，後來連續虧損跌回-30，最大回撤就有160，但最終
結算可能只是-33，這是正常的數學結果，不是計算邏輯有誤。

為了讓這種情況能被實際診斷(而不是只看到一個數字)，`compute_stats()`現在
會額外記錄「回撤高點發生時間」和「回撤谷底發生時間」，讓使用者能對照當時
的成交紀錄，判斷這段回撤到底是「一直穩定小賠累積」還是「曾經賺很多、後來
遇到一段逆風全部吐回去」——這兩種情況代表的策略體質完全不同，前者代表策略
方向判斷經常是錯的，後者代表策略本身可能是對的、但風控/單筆停損的幅度需要
更嚴謹。

已用「先連續獲利衝高、後連續虧損吐回、最終小賠收場」的合成情境測試過，
正確算出最大回撤跟總損益是兩回事，也正確標出高點/谷底發生的確切時間。

Dashboard的模擬單績效面板和歷史回測結果都新增了「最大回撤發生區間」的
文字說明，顯示高點/谷底各自的時間，可以直接對照下方的成交紀錄查看細節。

## 參數掃描（找出比較好的風控參數組合）

新增 `app/sweep.py`，一次改一個風控參數(其他維持目前dashboard設定面板的
數值)，跑約10組回測，自動比較哪個參數方向、哪個數值的勝率/總損益/獲利因子
比較好，不用手動一個一個試、自己記錄結果。

**設計取捨：** 用「一次只變動一個參數」的敏感度測試，而不是全部參數
排列組合的完整網格搜尋(full grid)——4個參數各3-4個候選值的完整網格會有
上百組，每組回測都要幾秒到十幾秒，跑不完。改成線性成長的組數(參數數量 x
候選值數量，目前約10組)，雖然沒辦法找到「全域最佳組合」，但足夠回答
「這個參數該調高還是調低」這個問題，實用性和運算時間之間取得平衡。

**運作方式：** 用背景執行緒跑(不是單一HTTP請求內等全部跑完)，避免請求
逾時。流程是「送出掃描 → 立刻拿到job_id → 前端每3秒輪詢一次進度」，
全部跑完通常需要1-2分鐘(用預設2天資料、10組回測)，可以先做其他事、
之後再回來看結果。

**Endpoint：**
- `POST /backtest/sweep?days=2&interval_seconds=60` — 啟動掃描，回傳`job_id`
- `GET /backtest/sweep/{job_id}` — 查詢進度和目前已完成的結果(隨背景執行緒
  跑完一組一組累積，不用等全部跑完才看得到部分結果)

已測試驗證：組合生成邏輯正確排除跟目前設定重複的候選值、背景執行緒完整
跑完所有組合、結果能正確依獲利因子排序。

**Dashboard新增「參數掃描」面板：** 選K線週期和用幾天資料，按「開始掃描」，
每3秒自動更新進度，結果依序列出每組的勝率/總損益/獲利因子，獲利因子最高
的那組會標記金色「★最佳」邊框，對照組(目前設定)有素色邊框方便辨識基準。

## ATR 動態停損（可選，預設關閉）

新增 `compute_atr()`(analysis.py)，用近期K棒的True Range移動平均，衡量市場
當下實際波動幅度，讓停損/移動停損距離可以跟著波動度自動調整——震盪劇烈時
自動放寬(避免被雜訊洗出場)，市場平靜時自動收緊(該停利/停損時不拖泥帶水)，
取代原本猜一個固定點數的做法。

**這不是取代，是可切換的選項：** 新增設定欄位`paper_use_atr_stops`(0=關閉
固定點數/1=開啟ATR動態)，以及三個倍數(`paper_atr_sl_multiplier`、
`paper_atr_trigger_multiplier`、`paper_atr_trail_multiplier`)，都在dashboard
「策略參數設定」面板可以直接調整。開啟時：
- 初始停損 = ATR × `paper_atr_sl_multiplier`
- 移動停損觸發距離 = ATR × `paper_atr_trigger_multiplier`
- 移動停損跟隨距離 = ATR × `paper_atr_trail_multiplier`

ATR資料不足時(剛啟動、K棒不夠)會自動退回固定點數模式，不會讓判斷卡住。

**即時模擬單和回測都支援**：`paper_trading.py`的`_tick()`每次都重新計算
當下ATR，用最新波動度決定距離；`backtest.py`的`run_backtest()`也在
walk-forward重播的每一步重新計算，正確模擬「停損距離跟著市場即時調整」的
效果，不是整場回測固定用同一個值。已用端到端測試驗證兩種模式(固定點數/
ATR動態)都能正常運作，且開關切換的行為符合預期。

**參數掃描也支援比較兩種模式**：`sweep.py`現在會自動多測一組「切換ATR開關」
的組合(如果目前是固定點數模式，就多測開啟ATR的版本，反之亦然)，可以直接在
掃描結果裡看到兩種停損機制哪個獲利因子比較好，不用猜。

**誠實的預期管理：** ATR只解決「停損距離該給多少空間」的問題，不會改變
訊號本身要不要進場的判斷。如果策略在震盪盤容易誤判方向，ATR能減少雜訊
造成的無謂停損(通常能改善獲利因子)，但不保證讓策略整體轉虧為盈——實際
效果請用參數掃描的數據判斷，不要只憑理論預期。

## 修正記錄：ATR模式開啟時，參數掃描測到無效參數

**發現的問題**：目前設定已經是ATR動態模式時，跑參數掃描，結果「初始停損=3.0/
8.0/12.0」這幾組數字全部跟對照組一模一樣。原因是`run_backtest()`在ATR模式

不管改成多少都不會影響結果——這不是計算錯誤，是掃描邏輯沒有考慮到「目前是
哪個模式」，測了在當下模式根本不會生效的參數。

**修正**：`sweep.py`的`_build_combos()`現在會依對照組目前的`paper_use_atr_stops`
狀態，只測「在這個模式下真的會影響結果」的參數——ATR模式開啟時測三個ATR倍數
(`paper_atr_sl_multiplier`等)，固定點數模式時測原本的三個固定點數參數，
兩者互斥、不會混測無效參數。已用兩種模式分別測試驗證：固定點數模式下正確

資料驗證ATR倍數不同時掃描結果確實會不同(修正前這裡全部都會一樣)。

`訊號反轉確認次數`跟`ATR開關切換`本身兩種模式下都有效，維持不變。

## 震盪濾網（可選，預設關閉）— 自動偵測震盪盤、暫停開新倉

之前發現連續幾次回測的最大回撤時間點很接近，一開始懷疑是「特定時段液體差」，
但釐清後發現是因為那幾次回測抓的都是「過去N天到現在」的重疊時間窗口，本來
就會抓到同一段行情——不是真的有規律的壞時段。真正該做的是「不管什麼時候，
自動偵測當下是不是震盪盤」，而不是綁定固定的日期/時段。

**新增 `compute_choppiness_index()`(analysis.py)**：業界常見的Choppiness Index
指標，不判斷方向，只判斷「市場現在有沒有在走出明確方向」。公式是「過去N根
K棒的True Range總和」跟「N根K棒的整體價格區間」的比值取對數：
- 數值越高(通常>61.8)代表越震盪：價格在原地反覆折返，沒有走出淨移動
- 數值越低(通常<38.2)代表趨勢越明確：價格有效率地朝同一方向移動

已用合成資料驗證：強趨勢盤算出CI≈3.4，震盪盤算出CI≈66.2，兩者區隔清楚。

**運作方式**：新增設定`paper_use_chop_filter`(開關)和`paper_chop_threshold`
(門檻，預設61.8)。開啟後，訊號升級成「訊號」階段時，如果當下Choppiness Index
超過門檻，就跳過這次開倉機會(現有部位不受影響，出場規則照常運作，濾網只
影響「要不要開新倉」，不影響已經開的倉位怎麼出場)。

即時模擬單和回測都支援，已用三種情境測試過：震盪時暫停開倉、趨勢時正常
開倉、濾網關閉時完全不受震盪指標影響。

**參數掃描也支援**：`sweep.py`新增震盪濾網門檻的敏感度測試(只在濾網開啟時
才測門檻數值，避免重蹈ATR那次的覆轍)，以及濾網開關切換的A/B對照組，方便
直接用數據判斷這個濾網對你的策略有沒有幫助。

## 修正記錄：5分K纏論在重部署後資料量偏少

**發現的問題**：重新部署後，5分K纏論分析常常只有很少的合併K棒數/分型數/筆數
(例如只有7根K棒、1筆走勢)，即使有接資料庫、啟動時會自動回填歷史資料。

**根本原因**：這不是重部署造成的新bug，是既有的結構性限制被重部署放大顯現——
5分K的一根K棒，平均要吃掉大約5倍於1分K的成交筆數才能湊滿，同樣的
`MAX_TRADE_HISTORY`(逐筆成交資料上限)對1分K來說綽綽有餘，對5分K卻一直偏緊，
尤其在服務重啟、記憶體歸零重新累積(或從資料庫回填)的當下特別明顯。

**修正**：把`MAX_TRADE_HISTORY`(binance_client.py)和`CHAN_LOOKBACK_TRADES`
(signal_engine.py)從20000提高到60000，順便同步了`db.py`的`load_recent_trades()`
預設值和`main.py`三個debug endpoint(`/analysis/candles`等)的預設trade_limit，
確保全部保持一致。

已用合成資料驗證：60000筆成交資料量下，5分K纏論運算耗時僅0.03秒(效能沒有
變差)，且能穩定拼出數十根K棒、二十幾筆走勢，遠比修正前的個位數健康。

## 追加調整：資料上限再提高到100000筆

實測驗證後，把`MAX_TRADE_HISTORY`/`CHAN_LOOKBACK_TRADES`從60000再提高到100000。
實測數據：
- 記憶體用量：約18MB(對一般Zeabur方案而言微不足道)
- 5分K運算耗時：0.06秒
- 15分K運算耗時：0.09秒，且能穩定拼出4個中樞、32筆走勢(60000筆時明顯較少)

多個中樞對「趨勢背馳 vs 盤整背馳」的判斷特別關鍵——趨勢背馳需要至少2個
不重疊的中樞才能成立，資料量不夠時這個判斷幾乎不會觸發，100000筆這個資料量
對15分K來說能穩定滿足這個條件。

記憶體和運算時間都遠遠不是瓶頸，可以放心採用。再往上加(例如到幾十萬筆)
邊際效益會遞減(太久遠的價格結構對短線判斷意義不大)，目前100000是合理的
平衡點，暫不建議繼續往上衝。

## 修正記錄：回測30天逾時失敗（Load failed）

**發現的問題**：拉長回測天數上限到30天後，實測跑30天回測會逾時失敗
(前端顯示「Load failed」，這是網路層級的請求逾時/連線中斷，不是後端
回傳的錯誤訊息)。

**根本原因**：回測「逐步重播」每一步要重新計算一次纏論，過去這裡直接
import即時資料流的`CHAN_LOOKBACK_TRADES`常數當作窗口大小上限。上一次
為了讓「即時」5分K/15分K纏論有足夠的真實時間跨度，把這個常數從20000
提高到100000——但這個理由完全不適用於回測：回測是**重複計算**，窗口
越大、單步成本越高，30天回測有1200步，等於把放大後的成本乘了1200遍。
實測：7天回測從15秒拖到18秒(還可接受)，但30天回測拖到57.6秒(僅本地
運算時間，還沒算進真實部署要跟Binance API來回抓K線的網路時間)，加總
起來很容易超過手機瀏覽器或Zeabur反向代理的逾時上限，導致連線在後端
還沒回應前就被中斷。

**修正**：新增`BACKTEST_CHAN_WINDOW_TRADES`(backtest.py專用，設20000，
就是先前已經驗證過「7天回測15秒內完成」的安全值)，取代原本直接import
`CHAN_LOOKBACK_TRADES`的做法，讓回測的重播窗口大小跟即時資料流的窗口
大小完全分開、互不影響。已重新測試驗證：7天回測13.0秒、30天回測15.8秒，
效能都恢復到合理範圍，而且即時資料流的5分K/15分K纏論(仍維持100000筆
窗口)完全不受影響。

**經驗教訓**：這是一個「共用常數，改一邊卻影響另一邊」的典型案例——
即時資料流和回測雖然都呼叫同一套訊號計算邏輯(`signal_engine.py`)，但
兩者的效能特性完全不同(即時是「持續運作、增量更新」，回測是「短時間內
大量重複計算」)，不該共用同一個影響效能的常數，即使兩者一開始數值剛好
一樣。之後如果還有類似「看起來相關、但用途情境不同」的常數，會優先考慮
是否應該一開始就分開設定，避免同樣的問題再發生。

## 修正記錄：績效統計數字沒有真正排除舊設定的交易

**發現的問題**：先前加的「分隔線」只在交易紀錄清單裡視覺上標示新舊分界，
但總筆數、勝率、獲利因子、最大回撤這些**統計數字**，其實還是拿包含舊設定

這樣改參數之後看到的績效數字仍然被舊設定的交易稀釋/扭曲，不符合「改完
參數就該用新參數底下的實際表現評估」的需求。

**修正**：`paper_trading.py`的`get_summary()`現在會用`settings_changed_at`
過濾出「進場時間晚於設定變更時間」的交易子集，只拿這個子集去算統計數字
(`compute_stats`/`assess_readiness`)；`recent_trades`清單本身仍然回傳完整
歷史(含分隔線)方便對照細節，只有上方的統計數字改成只反映新設定的表現。
回傳新增`stats_excluded_old_trades`欄位(排除了幾筆舊交易)，dashboard的
「目前策略設定」卡片會顯示這個數字，讓使用者清楚知道現在看到的統計數字
排除了多少筆舊資料。

**額外的精確化**：`settings.py`新增`TRADING_RELEVANT_KEYS`，只有「真正

已用三種情境測試驗證：只改達標門檻不會觸發排除、改交易相關參數會正確
觸發、混合修改(含交易相關欄位)也會正確觸發；並用模擬的新舊交易資料端到端
驗證統計數字確實只計算新設定生效後的子集(3筆舊交易+2筆新交易的情境下，
`total_trades`正確顯示2、`stats_excluded_old_trades`正確顯示3)。

## 修正記錄：K線圖5分K/15分K只顯示寥寥幾根K棒

**發現的問題**：Dashboard的K線圖切到5分K只顯示5-6根、15分K只顯示2根，
圖表幾乎沒有參考價值。

**根本原因**：K線圖呼叫`/analysis/candles`時，前端JS把`trade_limit`
**寫死成20000**，完全繞過了後端稍早已經調高的100000預設值——這是資料上限
調整時漏掉同步的殘留設定，5分K/15分K一根K棒要吃掉更多成交筆數才能湊滿，
20000筆對這兩個週期來說明顯不夠。

**修正**：拿掉`fetchCandles()`裡寫死的`&trade_limit=20000`，改成不帶這個
參數，直接讓後端用預設值(目前是100000)。這樣之後如果後端預設值再調整，
K線圖會自動跟著套用，不用兩邊分別維護、也不會再發生類似「調了後端卻忘記
調前端」的情況。已確認`/analysis/candles`回傳的是聚合後的K棒陣列(不是原始
逐筆成交)，拿掉限制不會讓回傳的資料量爆炸，payload大小只跟「聚合出幾根
K棒」有關。

## 修正記錄：Telegram通知太頻繁，同方向訊號短暫閃爍就重複發送

**發現的問題**：同一個方向的訊號（例如持續看空），短短幾分鐘內收到好幾則
內容幾乎一樣的Telegram通知。

**根本原因**：原本的防重複邏輯是「只要訊號階段掉出『訊號』等級，就清空
記錄」，導致同一個方向只要中間閃爍一次雜訊(例如短暫掉到「關注」又立刻彈回
「訊號」)，就會被誤判成「全新訊號」重新通知一次——訊號本身在震盪盤本來就
容易在「訊號/關注」邊界來回跳動，這個機制放大了雜訊的影響。

**修正**：`notifier.py`改成「冷卻時間」機制——同一個方向的訊號，兩則通知
之間至少要間隔`notify_cooldown_minutes`(新增設定欄位，預設15分鐘，可在
dashboard的策略參數設定面板調整)才會再發送一次；如果方向真的反轉(例如
從看空變看多)，不受冷卻時間限制，會立即通知，因為這種情況代表判斷真的
變了、值得馬上讓使用者知道。不再有「掉出訊號等級就清空記錄」的邏輯，
冷卻時間本身就足以避免同方向的重複騷擾。

已用完整情境測試驗證(包含直接重現使用者回報的bug情境)：
- 第一次看到訊號 -> 正確發送
- 立刻又是同方向(冷卻時間內) -> 正確不重複發送
- 訊號短暫閃爍到「關注」又彈回同方向「訊號」(原本會誤觸發的情境) -> 正確不重複發送
- 方向真的反轉 -> 正確立即發送，不受冷卻限制
- 冷卻時間已過、同方向再次出現 -> 正確可以再通知一次

新增設定欄位`notify_cooldown_minutes`不算「交易相關參數」(不影響模擬單
交易邏輯，只影響Telegram通知的發送頻率)，所以調整這個欄位不會觸發模擬單
績效統計的「新舊設定分界」機制。

## 重大改版：Telegram通知改成事件驅動，模擬單實際進場/出場才通知

**改版動機**：原本的通知邏輯是背景執行緒每30秒獨立重算一次訊號，跟「模擬單
引擎實際有沒有開倉」是分開的兩套邏輯，容易對不上——例如震盪濾網擋掉了某次
進場機會，但通知端不知道濾網存在，還是會發送「訊號」通知，使用者收到通知
卻在模擬單面板上找不到對應的交易紀錄，也造成通知頻率偏高的問題。

**改版內容**：改成事件驅動——`paper_trading.py`的模擬單引擎(1分K/5分K/15分K)
實際「開倉」或「平倉」時，直接呼叫`notifier.py`的`notify_trade_event()`發送
通知，不再自己獨立輪詢計算訊號。這樣通知內容永遠精確對應模擬單實際的操作，
不會再有「通知了但沒有對應交易」或「交易了但沒收到通知」的落差。

**訊息格式也改成類似真實下單通知的呈現方式**：
- 進場：方向、時間、價格
- 出場：方向、時間、價格、出場原因、損益(points)

這是為了讓之後接軌真正的MT5自動下單時，通知格式不用大改，先在模擬階段
就用同樣的呈現邏輯練習。

**架構簡化**：`notifier.py`不再需要自己的背景執行緒(不用獨立輪詢訊號)，
`start()`/`stop()`保留是為了main.py啟動流程的介面一致，但改成無操作
(沒有背景執行緒需要啟動/停止)。`health_monitor.py`也移除了「通知背景
執行緒是否還活著」的健康檢查(不再適用，因為沒有獨立執行緒了)——模擬單
引擎本身的心跳監控已經足夠涵蓋，因為通知現在是模擬單引擎內部直接觸發的。

先前為了「同方向訊號短暫閃爍避免重複通知」新增的`notify_cooldown_minutes`
設定欄位，在事件驅動架構下不再需要(因為每次通知都對應一個真實的開倉/平倉
事件，不會有「同一個訊號被重複判斷」的情況)，已經移除這個設定欄位。

已用完整情境測試驗證：開倉/平倉都正確觸發對應格式的通知、無循環引用問題、
沒設定Telegram時整個啟動/關閉流程依然正常運作不出錯。

## 新增：模擬單開倉卡片顯示即時報價與未實現損益

之前要判斷「目前這一單是賺是賠」，得往上滑到頁面最上方看現價，再自己心算
跟進場價的差距。現在直接在開倉中的卡片下方多一行，顯示現價和未實現損益，
不用再滑動比對。

**實作方式**：純前端改動，不用多打一次API。沿用主畫面`/signal/latest`
已經抓到的現價(存在一個全域變數`lastKnownPrice`裡)，模擬單卡片渲染時直接

空單現價高於進場價時正確顯示負值(空單方向反過來)。

## 新增：幣安期貨下單執行模組(測試網優先)

新增`app/execution.py`，讓系統能實際在幣安期貨(USDⓈ-M，目前鎖定XAUUSDT)送出
市價單，為之後接軌自動交易做準備。

**現階段刻意設計成獨立的手動測試模組，還沒自動接上模擬單引擎的開倉/平倉
事件**——因為現在同時有1分K/5分K/15分K三個模擬單引擎平行運作，如果三個都
自動對同一個真實帳戶的同一個部位下單，會互相打架(例如1分K想開多、5分K同時
想開空，兩邊會在同一個帳戶上互相抵銷，不會像模擬單那樣各自獨立追蹤)。這個
「哪個引擎負責真實下單」的設計問題還沒解決，所以先讓使用者能手動驗證整條
「認證 -> 換算部位大小 -> 下單 -> 查詢部位」的流程能不能跑通，自動接軌是
下一步、需要另外討論的決定。

**技術細節：**
- 端點依官方文件(2026/8/25版本)：正式環境`https://fapi.binance.com`、
  測試網(Demo Trading)`https://demo-fapi.binance.com`
- HMAC SHA256簽章邏輯已用官方文件提供的範例參數逐字元驗證過，完全正確
- `BINANCE_USE_TESTNET`預設值是`"1"`(測試網)，要故意設成`"0"`才會打正式
  環境，避免不小心接到真錢帳戶
- 部位大小換算：`數量 = 風險金額(USD) / 停損距離(points)`，因為幣安XAUUSDT
  是1張合約=1金衡盎司=每點1美元，已用實際數字驗證過(風險$20、停損5點 
  ->換算出4張，觸及停損時虧損剛好是$20)
- 沒設定`BINANCE_API_KEY`/`BINANCE_API_SECRET`時整個模組靜默停用，設計
  原則跟`db.py`/`notifier.py`一致
- 平倉時直接查詢帳戶實際部位大小來決定平倉數量(不是呼叫端自己算)，避免
  浮點數誤差或多筆疊加導致平倉數量對不上實際部位
- 平倉單一律加`reduceOnly`保護，避免手誤或邏輯錯誤意外開出反向部位

**新增API endpoint(手動測試用)：**
- `GET /execution/status` — 查詢模組是否啟用、目前是測試網還正式環境(不需密碼)
- `GET /execution/account?password=...` — 查詢帳戶餘額，驗證金鑰有沒有接對
- `POST /execution/test-order` — 手動測試開倉，`{"password","direction","risk_usd","sl_points"}`，
  會先檢查目前是不是測試網，正式環境會直接拒絕執行避免誤觸
- `POST /execution/test-close` — 手動測試平倉，`{"password","direction"}`

已用單元測試驗證：HMAC簽章邏輯(用官方文件範例逐字元比對)、部位大小換算邏輯、
未設定API金鑰時的防護機制(所有操作正確拒絕不崩潰)、預設值確認是安全的測試網。

**使用方式：** 先到Zeabur設定`BINANCE_API_KEY`/`BINANCE_API_SECRET`(去幣安帳戶
找「Demo Trading」選項生成測試網專用金鑰，不是正式帳戶的API金鑰)，部署後呼叫
`GET /execution/status`確認`testnet: true`，再用`GET /execution/account`確認
餘額查得到，最後用`POST /execution/test-order`送一筆小額測試單驗證整條流程。

## 自動接軌：指定單一週期同步真實(測試網)下單

**設計決策**：使用者測試過幣安測試網下單模組(開倉/平倉都成功)後，決定用
5分K的模擬單引擎接上帳戶自動下單，1分K/15分K繼續維持純模擬。

**新增設定欄位**(`settings.py`)：
- `execution_interval_seconds`(0=全部純模擬 / 60/300/900=指定該週期同步下單)——
  只能指定「一個」週期，避免三個引擎同時對同一個帳戶下單互相打架
- `execution_risk_usd`——每筆真實下單的風險金額，換算下單數量用

這兩個設定都不算「交易相關參數」(不影響模擬單的模擬損益計算，只影響是否
同步一個真實/測試網訂單這個平行的副作用)，所以不會觸發「新舊設定分界」
的績效統計排除機制。

**paper_trading.py整合**：`_open_position()`/`_close_position()`在記錄模擬單
之後，檢查`self.interval_seconds`是否等於設定的`execution_interval_seconds`，
是的話才呼叫`execution.py`同步送出真實(測試網/正式環境依`BINANCE_USE_TESTNET`
決定)市價單。下單結果(成功/失敗)包成`executed`參數傳給Telegram通知，讓使用者
從通知內容本身就能分辨這筆是「純模擬」還是「真的下單了」，不用切回dashboard確認。

**穩健性設計**：真實下單的呼叫包在獨立的try/except裡，任何失敗(例如帳戶還沒
簽署TradFi-Perps協議、餘額不足、網路問題)都不會影響模擬單本身的記錄和追蹤——
模擬單紀錄是這個系統的主要依據，真實下單只是附加的驗證動作，兩者的可靠性
完全解耦。

已用完整情境測試驗證：
- 指定5分K為執行週期時，只有5分K引擎的開倉/平倉會觸發真實下單，1分K/15分K
  完全不受影響
- Telegram通知正確反映三種狀態：純模擬(「目前僅模擬單」)、下單成功(「已同步
  在幣安測試網下單」)、下單失敗(「同步下單失敗，僅記錄模擬單」)
- 下單失敗時，模擬單本身的開倉狀態依然正常存在、不受影響

## 修正記錄：改動不相關的設定也會誤觸發績效統計的新舊分界

**發現的問題**：使用者只想改「真實下單週期」這個設定(不影響交易邏輯)，
按下「儲存變更」後，卻發現模擬單績效統計把32筆先前累積的交易全部排除，
變成從0筆重新開始算。

**根本原因**：dashboard的「儲存變更」按鈕會把整個表單**所有欄位**的目前
顯示值一起送出(不是只送使用者實際修改過的那一個)，這是原本就有的設計。
問題出在`update_settings()`只要看到某個欄位「有出現在送出的資料裡」就當作
「這個欄位被異動了」，不會檢查新值是否真的跟目前存的值不同——所以即使
`paper_sl_points`等交易相關欄位的值根本沒變，因為它們也隨著整份表單一起
被送出，就被誤判成「這些交易參數也被改動了」，錯誤觸發了績效統計的新舊
設定分界機制。

**修正**：`update_settings()`現在會先比對「新值」跟「目前存的值」是否
真的不同，只有真的不同才算「這個欄位被異動」，才會被納入`applied`(進而
影響`_last_changed_at`的更新判斷、以及要不要寫入資料庫)。這樣不管dashboard
的儲存邏輯是送整份表單還是只送修改過的欄位，都不會誤判。

已測試驗證兩種情境：(1)模擬dashboard送出整份表單、但使用者實際上只想改
`execution_interval_seconds`這個不影響交易的欄位，其他交易相關欄位的值
維持原樣不變——修正後正確不會觸發分界機制；(2)真的改動`paper_sl_points`
這種交易相關欄位的數值——依然正確觸發分界機制，功能沒有被破壞。

## 重大改版：真實下單改成固定口數 + 失敗原因直接顯示在通知裡

**改版動機**：原本`execution.open_position()`是「給風險金額+停損距離，反推
下單數量」，但ATR動態停損模式下每筆的停損距離都不一樣，用這種方式算出來的
部位大小會跟著每筆停損距離浮動，難以預期。使用者提出反過來想：**自己決定
固定的下單口數，系統回推「這個口數對應多少風險金額、佔帳戶餘額多少%」給
使用者參考，最終口數由使用者自己決定**——這樣部位大小本身是穩定可預期的，
風險則誠實地隨市場波動大小浮動。

**改動內容：**
- `execution.py`：`open_position()`改成直接接受`quantity`參數，不再需要
  `risk_usd`/`sl_points`。新增`estimate_risk(quantity, sl_points, account_balance)`
  做反向試算(給數量和停損距離，算出隱含的風險金額和風險百分比)，`account_balance`
  沒提供時會即時查詢帳戶餘額
- `settings.py`：`execution_risk_usd`欄位換成`execution_quantity`(固定下單口數)
- `paper_trading.py`：真實下單改用設定裡的固定`execution_quantity`，不再受
  當下的`sl_points`影響

**新增「部位風險試算」工具**(dashboard「設定」分頁)：輸入候選數量和停損距離，
按試算，顯示隱含的風險金額和佔帳戶餘額百分比——純參考，不會下單、不會改
任何設定，使用者確認滿意後自己把數量填進「真實下單口數」設定裡存起來。

**修正記錄：Telegram通知現在會顯示下單失敗的詳細原因**，之前只顯示「同步
下單失敗，請檢查執行模組狀態」這種籠統訊息，使用者得另外查伺服器log才知道
發生什麼事。現在`notify_trade_event()`新增`execution_error`參數，失敗時會把
幣安API回傳的實際錯誤代碼/訊息直接放進通知內容，例如「失敗原因：{'code':
-4411, 'msg': 'Please sign TradFi-Perps agreement contract fapi.'}」，使用者
從Telegram訊息本身就能診斷問題，不用切回後台查log。

**新增槓桿設定**：`execution.py`原本就有`set_leverage()`但從來沒有被實際
呼叫過，這次在dashboard新增「設定槓桿」按鈕，讓使用者能手動確認/設定槓桿
倍數，排除「槓桿設定不符預期導致下單被拒絕」這個潛在的失敗原因。

已用完整情境測試驗證：`estimate_risk()`正確算出風險金額和百分比、開倉時
正確使用固定口數(不再受停損距離影響)、下單失敗時錯誤原因正確出現在
Telegram通知裡。
